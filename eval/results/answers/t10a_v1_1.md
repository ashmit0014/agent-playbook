## Operating model (full version in `AGENTS.md`)

- **Goal, in your terms:** you run one command on a real bank export and get a file your budgeting app imports with no errors. Every transaction appears exactly once, with the right date, description and amount, exact to the cent and with the bank's sign kept. If the input isn't what we expect, the tool stops with an error instead of writing a file that looks right but isn't.
- **How we check it:**
  - **Parser:** I typed the expected values in by hand from the sample. Each row's balance must also equal the previous balance plus that row's amount, which is a check that uses the bank's own numbers rather than my reading of them.
  - **Whole tool:** your budgeting app actually importing a converted file, and you confirming the totals match the bank. Only you can run that check.
  - **Signs I won't treat as proof:** how many tests pass, my own tests on their own, "no error printed", and the 4-row sample standing in for a real export.
- **Biggest risk:** money or dates being misread without any error, so a wrong file imports cleanly. Examples: rounding errors from floating-point numbers, a lost minus sign, a quoted comma splitting a field, or day and month swapped. That's the part I tested first.
- **Who decides what:** I handle code structure, error handling and tests. You decide the app's exact import format, which bank date to use, the success criteria, and anything involving your real bank data.
- **Hard limits and what enforces them:**
  - **No pandas or other installs:** a test fails if the code imports anything outside Python's standard library.
  - **Your real exports stay private:** `.gitignore` keeps `real/` and `*.private.csv` out of git, and they never go to outside services.
  - **Recoverable history:** a local git repository, with no remote.
- **When I stop and ask you:**
  - a real export differs from the sample in a way that means guessing what it means;
  - the same bug survives two fixes;
  - anything external or that can't be undone.

## Questions only you can answer (my default in brackets)

1. **Which date should the output use:** the booking date or the value date? They differ on the RENT row (3rd vs 4th). [booking date]
2. **What columns does the app expect, in what order, and with or without a header row?** A sample file the app has accepted would settle this. [`Date;Description;Amount`, with a header]
3. **Which decimal mark should amounts use:** `-54,20` or `-54.20`? [comma, since DD.MM.YYYY and semicolons suggest a European format]
4. **What file encoding does the app expect?** [UTF-8, no BOM]
5. **Which Python version is on the machine it will run on?** [3.8 or later]
6. **Do real exports ever differ from the sample?** For example thousands separators like `1,234.56`, summary lines at the bottom, other encodings, or rows not in date order. A redacted real export would help, and it would never be committed. [none assumed]

## Built this session

- **`bankconv/parser.py`:** turns the bank CSV into typed records. It uses only Python's standard library, keeps amounts as exact decimals (`-54.20` stays `-54.20`, sign included) and dates as real dates, and keeps both the booking and value date. It is strict about the header, the number of fields per row, ISO dates and plain amounts. Anything unexpected stops it with an error that gives the line number; for example, `1,234.56` is rejected rather than guessed. It accepts a BOM, Windows line endings and a missing final newline.
- **`check_balance_chain()`:** the balance check described above, as a separate function.
- **Project files:** `AGENTS.md`, `CLAUDE.md`, `STATE.md` (30 lines), `DECISIONS.md`, `.gitignore` and `.gitattributes`. The last one stops git from changing the CSV line endings. The folder wasn't a git repository, so I created one locally.
